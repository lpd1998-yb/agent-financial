# 可观测性与评测

- Status: Accepted
- Owner: Project
- Last reviewed: 2026-09-23
- Scope: 定义研究执行的追踪、指标、固定评测集、质量门禁和反馈调优；不定义基础设施部署步骤或报告修订交互。
- Related ADRs: ADR-0001

## 1. 可观测目标

系统需要同时回答：

- 服务是否正常、任务是否停滞；
- 数据和证据是否新鲜、完整、可追溯；
- Agent 是否遵循计划并正确调用工具；
- 报告是否忠于数据和证据；
- 用户是否得到及时、可理解的研究产物；
- 每只股票、每个任务和每类模型花费多少。

产品可观测性由 AI 研究控制台提供，技术可观测性通过统一 Trace、结构化日志、指标和告警提供。基础设施“可用”不代表研究结论“可发布”。

## 2. ResearchRun 与 Trace

一次外部请求产生全链路 `traceId`，并连接：

```text
Feishu event
→ n8n execution
→ HTTP request
→ ResearchTask / ResearchRun
→ ExecutionNode
→ ToolCall / ModelCall
→ ResearchArtifact
→ QualityGateResult
→ ReportVersion
→ Notification
```

每个 `ExecutionEvent` 至少记录 `traceId`、`researchRunId`、`nodeId`、事件类型、时间、状态、尝试次数、输入/输出版本摘要、错误分类和费用引用。日志禁止记录凭据、完整敏感 Prompt、个人数据和未经脱敏的文档内容。

控制台从不可变事件构建投影，展示当前目标、等待原因、节点 DAG、产物、血缘和恢复操作。

## 3. 系统指标

- HTTP 请求量、错误率和延迟分位；
- ResearchRun 创建、完成、失败、停滞和恢复数量；
- 队列深度、节点等待时间和后台任务耗时；
- PostgreSQL 连接、查询延迟、容量和备份状态；
- OSS 上传、下载、永久查看和错误率；
- 飞书回调验签、通知成功率和重试；
- Tushare、模型、Embedding、OCR 和其他外部 API 成功率、限流与延迟；
- JVM、CPU、内存、磁盘、网络和容器重启。

第一版使用 JSON 日志、Spring Boot Actuator、Micrometer、OpenTelemetry、PostgreSQL 业务指标和阿里云监控。实际需要明确后再增加 Prometheus、Grafana 或日志服务。

## 4. RAG 指标

- 必要证据召回率；
- 有效证据比例和 `precision@k`；
- 元数据与历史时点过滤准确率；
- 重排后首条有效证据位置；
- Citation 支持度和页码有效率；
- 关键风险遗漏率；
- 重复召回、冲突证据和无效片段比例；
- PDF 下载、原生解析、OCR、页码映射和入库成功率；
- 低置信度表格与人工处理队列数量。

解析成功率与原始 PDF 可访问率分开统计。

## 5. 报告指标

报告按维度评价：

- 事实和数字正确性；
- 证据覆盖与引用有效性；
- 财务、增长、估值和同行逻辑；
- 风险与证伪条件覆盖；
- 事实、推断和市场观点的区分；
- 跨章节数字和结论一致性；
- 数据时点和结论新鲜度；
- 表达清晰度和结论稳定性。

不使用缺乏解释的单一总分替代分维度结果。

## 6. Agent 指标

- `AnalysisPlan` 正确率和程序校验拒绝率；
- 工具选择正确率、重复/无效调用率；
- 行业模板选择正确率；
- 证据不足时正确停止的比例；
- 局部重试成功率和全任务重跑比例；
- Schema 失败、调用上限和预算超限；
- 相同冻结输入下的结构化结果一致性；
- 模型路由原因与人工预期的一致性。

确定性检查优先。LLM Judge 只辅助语义评分，必须使用人工标注样本校准。

## 7. 产品与成本指标

- 首次分析、最新观点、快速查询和报告追问耗时；
- 日报、周报、月报和事件提醒按时完成率；
- 飞书任务受理到首次进度的延迟；
- 报告查看、证据跳转、反馈和修订使用情况；
- 用户认同度及问题类型分布；
- 单股票日报、单份周/月报、首次研究和单次查询成本；
- 模型 Token、Embedding、OCR、Tushare 和基础设施分摊；
- 缓存节省金额和局部重试节省金额。

每次执行写入 `CostLedger`。单次、每日和月度预算达到 70% 时提示，90% 时告警，100% 时暂停非必要生成；数据同步、重大风险检测和确定性计算继续运行。

第一版先积累实际数据，再制定正式 SLA，不能以未经运行验证的目标冒充服务承诺。

## 8. 固定评测集

初期建立 20～30 个版本化 A 股案例，覆盖：

- 高质量但高估值；
- 低估值但基本面恶化；
- 周期拐点和行业变化；
- 财报修订和会计口径变化；
- 重大风险与公告冲突；
- 数据缺失、PDF 解析失败和名称歧义；
- 多来源冲突；
- 历史时点分析；
- 无实质变化时不生成重复内容；
- 反馈修订后不再引入同类问题。

每个 `EvalCase` 保存固定 `asOfTime`、冻结输入、必须出现的事实、必须引用的证据、禁止结论、允许差异部分、预期工具轨迹和人工评分标准。数据集、案例和基线未来存放于 `evals/`。

## 9. 发布质量门禁

以下任一检查失败，报告或观点不得发布：

- 证券主体错误；
- 使用分析截止时间之后的数据；
- 核心数字不能在输入或计算中找到；
- 单位、币种、复权或报告期错误；
- Citation 不存在、版本错误或页码无效；
- 高重要度结论没有证据；
- 输出不符合 Schema；
- 违反工具、调用次数、预算或安全限制。

发布前按顺序执行离线评测、历史回归、影子运行和人工抽检。Prompt、模型、解析器、检索、计算或工作流的重要变化必须对比当前批准基线。

## 10. 反馈驱动的调优闭环

```text
用户反馈或生产异常
→ 归因到数据/计算、解析/检索、Prompt、模型、工作流或产品
→ 创建可复现 EvalCase
→ 修复并离线回归
→ 影子运行与人工对比
→ 小范围启用
→ 正式发布与持续监控
```

单用户场景不进行随机线上 A/B 测试，使用相同冻结输入的新旧版本对比。长期不以股价涨跌作为唯一标准，而检查当时公开信息是否遗漏、风险是否及时识别、证伪条件是否有效、观点是否及时变化，以及估值逻辑是否与后续基本面匹配。

反馈产品规则见 [反馈与报告修订](../product/feedback-and-revision.md)，执行节点见 [Agent 工作流](agent-workflow.md)。
